# Техническая архитектура

Утверждённая основа NAITMOR // ARCHIVE 2.0: Astro, TypeScript strict,
статический HTML и публикация в подкаталоге GitHub Pages через GitHub Actions.

## Основа этапа 1

Реализованы конфигурация проекта, общий HTML-шаблон, техническая главная,
страница 404, палитра CSS-переменных и функция внутренних URL.
Локальные файлы шрифтов, интерфейс разделов и клиентская интерактивность
относятся к следующим этапам. До подключения шрифтов используются системные.

## Разделение ответственности

- `content/`: авторские материалы без логики интерфейса.
- `schemas/` и `content.config.ts`: будущая валидация и типизация коллекций.
- `assets/images/`: изображения, обрабатываемые Astro при сборке.
- `public/`: файлы, которые нужно копировать без обработки.
- `config/`: технические настройки и будущая навигация.
- `lib/`: общие выборки и вспомогательные функции.
- `layouts/`: структура HTML-документа и страниц.
- `components/`: переиспользуемый интерфейс по назначению.
- `pages/`: маршруты, связывающие данные и компоненты.
- `scripts/` внутри `src/`: будущие клиентские сценарии.
- `scripts/` в корне: инструменты проверки проекта.

## Контентная архитектура этапа 2

Зарегистрированы семь коллекций из актуального задания: `characters`, `lore`,
`timeline`, `music`, `gallery`, `news`, `dossiers`. Старые пустые каталоги сохранены.
Схемы `src/schemas/` используются и Astro, и самостоятельным валидатором: отдельной
упрощённой схемы для служебных скриптов нет. Неизвестные поля запрещены.

`music` — discriminated union по `kind`: `release` или `track`. Подтип `format`
у релиза различает альбом, EP, сингл и сборник. Треклист релиза хранит ссылки
на записи треков, номер диска и позицию. Одна запись может входить в разные релизы.
Самостоятельная запись трека не обязана принадлежать альбому.

Ссылки преобразуются схемой в `{ collection, id }` с литеральным типом коллекции.
Граф проверяется до Astro check/build: существование целей, локаль, подтипы,
изоляция DEMO и черновиков, уникальность ключей и отсутствие циклов родительского лора.

`src/lib/content.ts` предоставляет production-выборки, отдельный preview,
поиск переводов, каталоги музыки, сортировку хронологии и общий поисковый набор.
`getCatalogEntries()` исключает unlisted-досье; `getSearchEntries()` исключает
весь CLASSIFIED. Прямое отображение опубликованных unlisted-записей возможно
через `getArchiveEntries()`, когда будут добавлены маршруты.

Записи хранятся в Markdown/MDX, JSON или YAML; текст и файлы медиа отделены от UI.
Текстовые семантические ссылки `content:` проверяются по графу. Их преобразование
в HTML-ссылки является обязанностью будущего слоя отображения.

MDX подключён интеграцией 8.1.5, совместимой с Astro 7.4.11. Исполняемый редакционный
MDX запрещён валидатором: поддерживаются только описанные статические элементы.

## Локализация

Каждая запись содержит один `locale`: `ru` или `en`, и лежит в соответствующей папке.
У переводов общий `translationKey`; прямые смысловые ссылки остаются в одной локали.
Словари UI типизированы, английский набор обязан содержать все русские ключи.
Подмена отсутствующего перевода записью другого языка не выполняется.

Astro i18n использует русский язык по умолчанию без префикса. Контракт будущих
английских маршрутов — `/en/` внутри существующего GitHub Pages base.
Один вызов `getContentUrl()` централизует адреса коллекций; он не создаёт страницы.
Проверка письменности не заменяет редакционную проверку качества перевода.

## DEMO

20 записей, по 10 на язык: два персонажа, эпоха и понятие лора, событие,
альбом и трек, метаданные арта, новость и досье. Все отмечены `demo: true`,
их заголовки и ключи явно содержат DEMO. Реальных изображений и аудио нет.
Production-выборки исключают DEMO независимо от `draft`.

## Маршруты

Подготовлены каталоги `characters`, `lore`, `timeline`, `music/releases`,
`music/tracks`, `gallery`, `classified`, `news`. Их страницы появятся
на этапе интерфейса; коллекции и пустые каталоги сами не создают URL.

Astro формирует статическую сборку в `dist/`. Canonical URL строится
от настроенного `site`, внутренние ссылки — через `withBase()`.
Проверка `npm run check:pages` контролирует префикс проекта в собранном HTML.

## Воспроизводимость

Версия Node.js закреплена в `.node-version`, прямые зависимости — в `package.json`,
полное дерево — в `package-lock.json`. В CI и при повторной установке используется
`npm ci`. `npm run check` выполняет валидацию контента, регрессионные тесты и
Astro/TypeScript. `prebuild` повторяет контентную проверку до production build.

Публикация отделена от CI и имеет только ручной триггер.
